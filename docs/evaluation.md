# 평가

숫자가 부풀지 않게 어떻게 쟀는지, 버전마다 숫자가 어떻게 바뀌었는지 정리한다.

## 결과

**묶기:** 레코드 5,128건 → 상품 4,855개(5.3% 줄임). 2건 이상 묶인 상품은 253개다. 그 밖에 OEM 형제·단어 차이 링크 338쌍, 검수 대기 433쌍이 있다.

**품질 (최종 시험, 2026-10-26):**

| 지표 | 값 |
| --- | --- |
| 정밀도 (자동으로 묶은 쌍이 정말 같은 상품인 비율) | **92.0%** (46/50, 95% 신뢰구간 약 81~97%) |
| 재현율 (같은 상품 쌍 중 자동으로 묶은 비율) | **81.4%** |
| 검수 포함 재현율 | 100% (표본 기준, 못 묶은 5쌍 모두 검수 대기에 있음) |

시험 방법은 다음과 같다. 숫자가 부풀지 않게 하려고 이렇게 했다.

- 규칙을 **동결**했다. 코드·결과 파일 16개의 SHA-256 해시를 기록해 두고, 하나라도 다르면 평가가 멈춘다.
- 앞선 정답셋(1·2차)에 나온 레코드 341개가 들어간 쌍은 모두 뺐다.
- 결과 구간 6개에서 층화로 170쌍을 뽑았다. 라벨을 달 때는 어느 구간인지, Jev 점수가 몇인지 보지 않았다. 라벨을 저장한 뒤 **평가는 한 번만** 했다.
- 구간 크기로 가중해 전체 값을 추정했다([`scripts/eval/final-evaluate.ts`](../scripts/eval/final-evaluate.ts)).

| 버전 | 정밀도 | 재현율 | 비고 |
| --- | --- | --- | --- |
| 규칙만 | 100% | 77% | 1차 정답셋 50쌍 |
| 규칙 + Jev (첫판) | 75% | 92% | Jev가 높은 확신으로 틀린 쌍이 섞임 |
| 규칙 + Jev (개선 후) | 92% | 92% | 같은 50쌍으로 고쳐서 과대 |
| 같은 버전, 새 표본 | 93% | **59%** | 2차 정답셋으로 처음 재 보니 재현율이 크게 낮았다 |
| **최종 (동결)** | **92.0%** | **81.4%** | 위 시험 방법 |

## 다시 재 보기

```bash
node scripts/normalize.ts 닭가슴살 --services=C002   # 시험은 C002 5,128건 기준
node scripts/candidates.ts 닭가슴살
node scripts/run-grouping.ts 닭가슴살
node scripts/eval/final-evaluate.ts 닭가슴살         # 해시 확인 → 정밀도·재현율
```

- 원본 수집 데이터와 Jev 판정 캐시는 저장소에 없다(`data/raw`, `data/work`). 수집(`ingest.mjs`)과 판정(`judge.ts`)을 먼저 돌려야 한다.
- **재현 기록:** 동결(2026-10-26) 뒤 파일을 옮기고 실행 스크립트(사람 판정 반영, C006 옵션)를 고쳤다. 규칙 코드(`lib/` 4개)와 후보 쌍 파일은 바이트까지 같다. C002만 다시 정제해 같은 점수(92.0% · 81.4% · 100%)가 나오는 것을 확인했다. 그 뒤 지금 파일 해시 22개를 [`final-key.json`](../data/labels/닭가슴살/final-key.json)의 `reproduced`에 따로 기록했다. 처음 동결 기록(`frozen`)은 그대로 두었다.
- 1·2차 평가: `scripts/eval/round1-evaluate.ts`, `scripts/eval/round2-evaluate.ts`. 정답셋 설명은 [`data/labels/README.md`](../data/labels/README.md).
