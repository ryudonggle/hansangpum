# 확장 계획

지금은 닭가슴살 한 카테고리(5,128건)라 단계별 JSONL 파일 + Postgres로 충분하다.
C002 전체(약 108만 건)와 축산물 C006(약 57만 건)을 합치면 약 165만 건이다.
원본은 수백 MB~1GB 수준이라 **저장은 병목이 아니다.** 전부 짝지으면 약 1.4조 쌍이 되므로 병목은 **쌍 비교와 매번 전체를 다시 돌리는 방식**이다.

## 1. 후보 쌍은 블록 안에서만 (blocking)

- 같은 업체(company_root)·같은 식품유형 안에서만, 또는 이름 3글자 조각(trigram)이 겹치는 레코드끼리만 비교한다.
- 지금 후보 생성도 같은 방식이라, 규모가 커져도 쌍 수는 레코드 수에 거의 비례해서만 늘어난다.

## 2. 증분 처리

- 변경일(CHNG_DT)을 보고 새로 생기거나 바뀐 레코드만 다시 정제한다.
- 후보 쌍은 그 레코드가 들어간 쌍만 새로 만들고, Jev도 새 쌍만 묻는다.
- 판정 캐시(`pair_judgments`)는 지금처럼 쌍 키로 쌓으므로 그대로 쓴다.
- GitHub Actions로 매일 돌린다.

## 2-1. Jev 판정 비용 추정

실측 (닭가슴살, `data/work/judgments-닭가슴살.jsonl`):

| 항목 | 값 |
| --- | --- |
| 판정한 쌍 | 2,849쌍 (규칙을 다듬기 전 첫 판정) |
| 입력 토큰 | 3,037,004 (쌍당 약 1,070토큰) |
| 비용 | $0.127 (입력 $0.042/100만 토큰, 출력 무료) |
| 지금 규칙 기준 애매한 쌍 | 314쌍 → 다시 돌려도 약 34만 토큰, 약 $0.014 |

이름 글자 차이 같은 유형을 규칙으로 옮겨 Jev가 보는 쌍이 약 89% 줄었다.

165만 건 규모 추정. 레코드 1건당 애매한 쌍은 카테고리마다 다르다:

| 카테고리 | 레코드 | 애매한 쌍 | 레코드당 |
| --- | --- | --- | --- |
| 닭가슴살 | 5,128 | 314 | 0.06 |
| 라면 | 1,996 | 534 | 0.27 |
| 요거트 | 2,771 | 745 | 0.27 |

| | 낮게 (0.06) | 높게 (0.27) |
| --- | --- | --- |
| 160만 건 애매한 쌍 | 약 10만 쌍 | 약 43만 쌍 |
| 입력 토큰 | 약 1억 | 약 4.6억 |
| 전체 1회 판정 | 약 $4 | 약 $19 |
| 하루 신규 4,000건 증분 | 하루 약 $0.01 | 하루 약 $0.05 (월 $1.5 이하) |

- 라면·요거트 후보는 규칙을 다듬기 전에 만든 것이라 애매한 쌍이 실제보다 많을 수 있다. 높은 쪽은 보수적인 값이다.
- 같은 회사 계열 안에서만 비교하므로, 레코드가 많은 대기업 계열에서는 쌍 수가 레코드 수보다 빠르게 늘 수 있다.
- 판정은 쌍 키로 캐시하므로 같은 쌍을 다시 묻지 않는다.

## 3. 단계별 저장 형식

| 단계 | 지금 | 커지면 | 이유 |
| --- | --- | --- | --- |
| 원본 | `data/raw/*.jsonl` | 날짜별 JSONL.gz를 S3 같은 오브젝트 저장소에 | 받은 그대로의 기록. 덧붙이기만 하므로 JSONL이 맞다 |
| 정제·후보·점수 | `data/work/*.jsonl` | Parquet + DuckDB | 열 단위 압축. 서버 없이 수백만 행을 SQL로 몇 초 만에 처리 |
| 서비스 | Supabase Postgres | 그대로 | 묶음·레코드·검수는 수백만 행이어도 인덱스로 충분 |

계산은 다시 돌리기 쉬운 파일에서 하고, 서비스에 필요한 결과만 DB에 올리는 지금 구조를 유지한다.
파일과 DB가 어긋날 수 있으므로 `run-grouping`은 Jev 판정이 없는 애매 쌍이 있으면 멈춘다.

## 4. 검색

- pg_trgm이 느려지면 Elasticsearch/OpenSearch로 옮긴다.
- 그때 pg_trgm과 ES의 검색 품질·속도를 같은 검색어로 비교한다.

## 5. 로그 (`events`)

- 가장 빨리 커지는 표다.
- 월별 파티션으로 나누고, 매일 BigQuery(또는 ClickHouse)로 복사해 분석은 그쪽에서 한다.
- 트래픽이 커지면 `/api/events`가 DB에 바로 쓰지 않고 큐(Kafka 등)에 넣게 바꾼다.

## 6. 작업 순서 관리

- 단계가 늘면 수집 → 정제 → 후보 → 판정 → 묶기 → 적재를 Airflow 같은 도구로 묶는다.
- 단계마다 결과 건수와 검수 비율을 남겨, 규칙이나 데이터가 바뀐 날을 바로 알 수 있게 한다.

## 7. 데이터·판정 범위

- **축산물(C006):** C002에는 축산물이 없어 햄·소시지·양념육 같은 가공 닭가슴살이 빠져 있다. C006은 C002와 필드가 같으므로 함께 수집해 같은 파이프라인에 넣는다. 넣은 뒤에는 새 최종 시험이 필요하다.
- **다른 카테고리:** 라면·요거트는 수집·정제·후보까지 해 두었다. 카테고리마다 이름 규칙이 달라(맛 이름·용량·묶음 포장) 정답셋을 따로 만든다.
- **LLM 리포트:** 검수 대기·검색 0건 로그를 모아 "어떤 규칙을 더 넣을지" 제안하는 주간 요약을 만든다.
