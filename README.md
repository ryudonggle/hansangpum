# 한상품 — 공공데이터 품목제조보고를 소비자 상품 단위로 묶기

식품안전나라 품목제조보고(C002)는 공장·연도별로 레코드가 따로 쌓여, 소비자에게는 같은 상품이 여러 줄로 흩어져 보인다.
규칙 + Jev 판정 + 사람 검수로 이를 "같은 상품 / OEM 형제 / 다른 상품"으로 나눠 묶는다.

- 사이트: https://hansangpum.vercel.app (검색 · 상품 상세 · `/admin` 검수·지표)
- 스택: Next.js 16 · Vercel(icn1) · Supabase Postgres(서울) + Drizzle · pg_trgm 검색 · TypeSafe Jev · Vitest
- 범위: '닭가슴살'이 이름·원재료에 들어간 C002 레코드 5,128건

## 문제

품목제조보고는 제조소(공장)별·재신고별로 따로 올라간다. 그래서 같은 소비자 상품이 여러 레코드가 된다.
레코드 하나를 상품 페이지 하나로 쓰면 두 가지가 나빠진다.

- 검색 결과에 같은 제품이 반복된다.
- 이미지·구매 링크·영양 정보를 레코드마다 따로 붙여야 한다. 예: 하림 닭가슴살갈릭은 레코드 2개 중 1개에만 이미지가 있다.

**목표:** 레코드 N건을 소비자 상품 M개로 묶고, 그 품질을 정밀도·재현율로 잰다.
묶음 단위로 한 번만 매칭하면 이미지·링크가 묶음 전체로 퍼진다.

어려운 점은 "이름이 비슷하다"와 "같은 상품이다"가 다르다는 것이다.

- 같은 공장 안에서 이름이 한 단어만 다르면 대개 다른 맛이다(갈릭 ↔ 수비드 갈릭허브, 군만두 ↔ 물만두).
- 반대로 같은 상품인데 재신고하면서 이름이 바뀌기도 한다.

## 접근

```
수집(C002) → 정제 → 후보 쌍 → 규칙 점수 ─┬─ 확실히 같음 ──────────────┐
                                          ├─ 확실히 다름(cannot-link)  ├→ 묶기 → 적재 → 검색·상세
                                          └─ 애매함 → Jev ─┬─ 자동 ────┘
                                                           └─ 검수 대기 → /admin 사람 판정 → 다시 묶기
```

1. **관계를 셋으로 나눈다.** OEM 공장(예: 엄지식품)은 같은 레시피를 여러 브랜드(마니커·하이밥·허닭…)로 낸다. 이런 쌍은 "같은 상품"으로 묶지 않고 "OEM 형제"로 링크만 건다.
   - **같은 상품:** 묶는다.
   - **OEM 형제:** 묶지 않고 상세 화면의 "같은 회사 비슷한 상품"에 링크로 건다.
   - **다른 상품:** 따로 둔다.
2. **정제(`lib/normalize.ts`):** 중량·입수·판매처·보관(냉동/실온)·포장·이유식 단계를 이름에서 떼어 따로 둔다. 브랜드·맛은 이름 키에 남긴다. 회사명은 법인 표기·공장명을 떼어 같은 회사 계열로 맞춘다.
3. **후보 쌍(blocking, `lib/score.ts`):** 같은 회사 계열 안에서만 비교한다. 점수는 이름 bigram 유사도, 원재료 Jaccard, 식품유형 일치로 낸다.
4. **규칙이 먼저 정한다.**
   - 이름이 같거나 회사 접두어만 다르면 묶는다.
   - 보관·포장·단계·이름 속 숫자가 다르거나, 양쪽에 서로 다른 글자가 있으면 따로 둔다.
5. **애매한 쌍만 Jev 판정(`lib/judge.ts`):** TypeSafe Jev의 Choice로 세 관계의 확률을 받는다. 판정 기준(instructions·criteria)은 직접 정의했다. 결과는 쌍 키로 캐시해서 같은 쌍은 다시 묻지 않는다.
   - 자동으로 묶는 경우: 같은 상품 확률 0.7 이상이면서 어순·띄어쓰기만 다른 쌍
   - 그 밖의 애매한 쌍은 검수 대기로 보낸다.
   - 비용: 첫 판정 2,828쌍, 입력 300만 토큰, $0.127
6. **묶기(`lib/group.ts`):** union-find로 묶는다. A=B, B=C로 이어져 서로 다른 A·C가 섞이는 것을 두 단계로 막는다.
   - **cannot-link:** 확실히 다른 쌍이 하나라도 걸리면 두 묶음을 합치지 않는다.
   - **다수결:** 두 묶음 사이 쌍들의 표가 같음 > 다름일 때만 합친다.
7. **사람 검수(`/admin`):** 검수 대기 쌍마다 같음 / OEM / 다름을 고른다. `npm run regroup`을 돌리면 사람 판정이 규칙·Jev보다 먼저 적용되고 사이트에 다시 적재된다.
8. **로그(`/api/events`):** 검색·결과 클릭·상세 보기·외부 링크 이동을 직접 설계한 `events` 표에 쌓는다. `/admin`에서 14일 지표와 검색 0건 검색어를 본다. 세션 id는 브라우저 임의 UUID이고 개인정보는 남기지 않는다.

## 결과

**묶기:** 레코드 5,128건 → 상품 4,855개(5.3% 줄임). 2건 이상 묶인 상품은 253개다. 그 밖에 OEM 형제·단어 차이 링크 338쌍, 검수 대기 433쌍이 있다.

**품질 (최종 시험, 2026-10-26):**

| 지표 | 값 |
| --- | --- |
| 정밀도 (자동으로 묶은 쌍이 정말 같은 상품인 비율) | **92.0%** (46/50, 95% 신뢰구간 약 81~97%) |
| 재현율 (같은 상품 쌍 중 자동으로 묶은 비율) | **81.4%** |
| 검수 포함 재현율 | 100% (표본 기준, 못 묶은 5쌍 모두 검수 대기에 있음) |

시험 방법은 다음과 같다. 숫자가 부풀지 않게 하려고 이렇게 했다.

- 규칙을 **동결**했다. 코드·결과 파일 16개의 SHA-256 해시를 기록해 두고, 하나라도 다르면 평가가 멈춘다.
- 앞선 정답셋(1·2차)에 나온 레코드 341개가 들어간 쌍은 모두 뺐다.
- 결과 구간 6개에서 층화로 170쌍을 뽑았다. 라벨을 달 때는 어느 구간인지, Jev 점수가 몇인지 보지 않았다. 라벨을 저장한 뒤 **평가는 한 번만** 했다.
- 구간 크기로 가중해 전체 값을 추정했다(`scripts/evaluate-test.ts`).

| 버전 | 정밀도 | 재현율 | 비고 |
| --- | --- | --- | --- |
| 규칙만 | 100% | 77% | 1차 정답셋 50쌍 |
| 규칙 + Jev (첫판) | 75% | 92% | Jev가 높은 확신으로 틀린 쌍이 섞임 |
| 규칙 + Jev (개선 후) | 92% | 92% | 같은 50쌍으로 고쳐서 과대 |
| 같은 버전, 새 표본 | 93% | **59%** | 2차 정답셋으로 처음 재 보니 재현율이 크게 낮았다 |
| **최종 (동결)** | **92.0%** | **81.4%** | 위 시험 방법 |

## 발견과 교훈

**데이터**
- **OEM 공장이 핵심 변수였다.** 이름과 원재료가 거의 같아도 브랜드가 다르면 소비자에게는 다른 상품이다. 이 때문에 "같다 / 다르다" 두 갈래가 아니라 OEM 형제까지 세 갈래가 필요했다.
- **C002에는 축산물이 없다.** 햄·소시지·양념육 같은 가공 닭가슴살은 축산물 품목제조보고(C006)에 따로 있다. 카테고리를 '닭가슴살'로 잡아도 시중 상품의 상당 부분이 빠진다.

**판정**
- **Jev가 높은 확신으로 틀린 쌍은 대부분 "이름 글자 차이" 유형이었다.** 예: 된죽↔죽, 덮밥 400↔500, 바게트샌드↔샌드(0.78), 아욱(0.98), 마라꿔바로우(0.91). 코드로 알 수 있는 차이(숫자·단계·라인 코드·한쪽에만 붙은 글자)는 규칙으로 옮겼다. Jev는 어순·띄어쓰기만 다른 애매한 쌍에만 쓴다.
- **판정 하나가 다리가 되어 묶음이 섞인다.** 7건짜리 묶음이 실제로는 곤약볶음밥 / 야채 곤약볶음밥 / 허닭, 세 상품이었다. 쌍 판정이 맞아도 연쇄로 합쳐지면 틀린다. 그래서 cannot-link와 묶음 사이 다수결을 넣었다.
- **애매한 것은 묶지 않고 미룬다.** 정밀도를 지키려고 애매한 쌍은 자동으로 묶지 않고 검수로 보냈다. 최종 시험에서 못 묶은 5쌍은 모두 검수 대기에 있었다. 자동 재현율 81%는 사람이 433쌍을 보면 채워지는 값이다.

**평가**
- **정답셋을 보며 규칙을 고치면 숫자가 부푼다.** 1차 정답셋에서 재현율은 85~92%였지만 새 표본에서는 59%였다. 그래서 마지막 시험은 규칙을 동결하고, 겹치는 레코드를 빼고, 한 번만 쟀다.
- **표본 한 쌍이 추정치를 크게 흔든다.** 후보 쌍 밖에서 뽑은 1쌍(이름이 바뀐 재신고)이 "못 묶음" 추정치의 절반을 차지했다. 그래서 숫자와 함께 신뢰구간을 적는다.

**배포**
- **Vercel 함수가 동결됐다 깨면 끊긴 DB 연결을 그대로 쓴다.** 그 때문에 쿼리가 TCP 시간 초과까지 25~75초 멈췄다. 마지막 사용 후 10초가 지난 연결은 버리고 새로 열게 했고(새 연결 약 70ms), 연결 오류가 나면 한 번 재시도한다.
- **연결을 1개로 묶으면 동시 쿼리가 멈춘다.** 동시 쿼리가 한 연결에 겹쳐 보내지면서(pipelining) Supabase Transaction pooler에서 멈췄다. /admin은 쿼리 4개를 동시에 보낸다. 연결 수를 4로 늘려 해결했다.

## 한계

- **라벨러 = 규칙 설계자.** 정답셋 3개(50·140·170쌍)는 모두 Claude가 API 없이 직접 라벨했다. 사람이 단 라벨이 아니고, 규칙을 만든 쪽의 판단이 정답에도 들어가 있다. 사람 검수(`/admin`)가 쌓이면 그 판정으로 다시 잰다.
- **같은 회사 계열 안에서만 비교한다.** 서로 다른 회사가 낸 같은 상품(예: 유통사 PB를 다른 제조사가 맡은 경우)은 후보에 오르지 않는다. 시험의 모집단도 같은 회사 계열 안의 쌍이다.
- **한 카테고리만 검증했다.** 라면·요거트는 정제·후보까지만 돌렸고 정답셋이 없어 정확도를 모른다. Jev 판정 기준의 예시도 닭가슴살 전용이다.
- **표본이 작다.** 자동 묶음 표본은 50쌍이라 정밀도 신뢰구간이 81~97%로 넓다.
- **최종 숫자는 동결 버전에만 해당한다.** 이후 규칙이나 데이터(C006 추가 등)를 바꾸면 새 시험셋으로 다시 재야 한다.
- **검수는 아직 0건이다.** 검수 루프(`npm run regroup`)는 연결했지만, 실제 사람 판정으로 묶음을 바꾼 적은 아직 없다.

## 실행

```bash
node scripts/ingest.mjs 닭가슴살 <조건...> [--service=C006]   # 수집 → data/raw/
node scripts/normalize.ts 닭가슴살      # 정제
node scripts/candidates.ts 닭가슴살     # 후보 쌍·규칙 점수
node scripts/judge.ts 닭가슴살          # 애매한 쌍 Jev 판정 (캐시: 판정한 쌍은 다시 묻지 않음)
node scripts/run-grouping.ts 닭가슴살   # 묶기 → data/work/groups-닭가슴살.json
node scripts/load.ts 닭가슴살           # Supabase 적재
npm run regroup                         # /admin 사람 판정 내려받기 → 묶기 → 적재
```

## 데이터 출처와 주의

- **출처:** 식품의약품안전처 식품안전나라 Open API, 품목제조보고(원재료) C002. 상품명·업체명·원재료는 이 공공데이터를 그대로 쓴다.
- **저장소에 포함된 것:** 정답셋(`data/labels/`)에는 실제 상품명·업체명과 판정 메모가 들어 있다. 원본 수집 데이터(`data/raw/`)와 중간 결과(`data/work/`)는 넣지 않았다. `ingest.mjs`로 다시 받을 수 있다.
- **주의:** 포트폴리오용 실험이다. 묶음과 "OEM 형제" 링크는 자동 판정 결과라 틀릴 수 있다(자동 묶음 정밀도 약 92%). 특정 업체의 실제 제조·위탁 관계를 확인한 정보가 아니다.
- **남용 방지:** `/api/events`는 IP마다 1분 60건, 전체 1시간 5,000건까지 받는다. `/admin` 로그인은 IP마다 2시간 5번, 전체 1시간 30번까지 시도할 수 있다. IP는 저장하지 않고 서버 비밀값으로 서명한 해시만 센다(`lib/rate-limit.ts`).

## 확장 계획

지금은 닭가슴살 한 카테고리(5,128건)라 단계별 JSONL 파일 + Postgres로 충분하다.
C002 전체(약 108만 건)와 축산물 C006(약 57만 건)을 합치면 약 165만 건이다.
원본은 수백 MB~1GB 수준이라 **저장은 병목이 아니다.** 전부 짝지으면 약 1.4조 쌍이 되므로 병목은 **쌍 비교와 매번 전체를 다시 돌리는 방식**이다.

### 1. 후보 쌍은 블록 안에서만 (blocking)

- 같은 업체(company_root)·같은 식품유형 안에서만, 또는 이름 3글자 조각(trigram)이 겹치는 레코드끼리만 비교한다.
- 지금 후보 생성도 같은 방식이라, 규모가 커져도 쌍 수는 레코드 수에 거의 비례해서만 늘어난다.

### 2. 증분 처리

- 변경일(CHNG_DT)을 보고 새로 생기거나 바뀐 레코드만 다시 정제한다.
- 후보 쌍은 그 레코드가 들어간 쌍만 새로 만들고, Jev도 새 쌍만 묻는다.
- 판정 캐시(`pair_judgments`)는 지금처럼 쌍 키로 쌓으므로 그대로 쓴다.
- GitHub Actions로 매일 돌린다.

### 3. 단계별 저장 형식

| 단계 | 지금 | 커지면 | 이유 |
| --- | --- | --- | --- |
| 원본 | `data/raw/*.jsonl` | 날짜별 JSONL.gz를 S3 같은 오브젝트 저장소에 | 받은 그대로의 기록. 덧붙이기만 하므로 JSONL이 맞다 |
| 정제·후보·점수 | `data/work/*.jsonl` | Parquet + DuckDB | 열 단위 압축. 서버 없이 수백만 행을 SQL로 몇 초 만에 처리 |
| 서비스 | Supabase Postgres | 그대로 | 묶음·레코드·검수는 수백만 행이어도 인덱스로 충분 |

계산은 다시 돌리기 쉬운 파일에서 하고, 서비스에 필요한 결과만 DB에 올리는 지금 구조를 유지한다.
파일과 DB가 어긋날 수 있으므로 `run-grouping`은 Jev 판정이 없는 애매 쌍이 있으면 멈춘다.

### 4. 검색

- pg_trgm이 느려지면 Elasticsearch/OpenSearch로 옮긴다.
- 그때 pg_trgm과 ES의 검색 품질·속도를 같은 검색어로 비교한다.

### 5. 로그 (`events`)

- 가장 빨리 커지는 표다.
- 월별 파티션으로 나누고, 매일 BigQuery(또는 ClickHouse)로 복사해 분석은 그쪽에서 한다.
- 트래픽이 커지면 `/api/events`가 DB에 바로 쓰지 않고 큐(Kafka 등)에 넣게 바꾼다.

### 6. 작업 순서 관리

- 단계가 늘면 수집 → 정제 → 후보 → 판정 → 묶기 → 적재를 Airflow 같은 도구로 묶는다.
- 단계마다 결과 건수와 검수 비율을 남겨, 규칙이나 데이터가 바뀐 날을 바로 알 수 있게 한다.

### 7. 데이터·판정 범위

- **축산물(C006):** C002에는 축산물이 없어 햄·소시지·양념육 같은 가공 닭가슴살이 빠져 있다. C006은 C002와 필드가 같으므로 함께 수집해 같은 파이프라인에 넣는다. 넣은 뒤에는 새 최종 시험이 필요하다.
- **다른 카테고리:** 라면·요거트는 수집·정제·후보까지 해 두었다. 카테고리마다 이름 규칙이 달라(맛 이름·용량·묶음 포장) 정답셋을 따로 만든다.
- **LLM 리포트:** 검수 대기·검색 0건 로그를 모아 "어떤 규칙을 더 넣을지" 제안하는 주간 요약을 만든다.
